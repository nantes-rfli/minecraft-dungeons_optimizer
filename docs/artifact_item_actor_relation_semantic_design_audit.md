# Artifact `ItemActorClass` Formal Relation semantic design audit

## Decision

Baseline: GitHub `main` at `5796c70774c92672b87b40354e2194dd4c03292d` (after PR #145). This is a design audit only. The exact next Relation wave is **11/11 Artifact root `ItemActorClass` edges**, represented by a new `RelationKind = item-actor`. The name denotes a source item's configured **native `ItemActor` subclass**. It does not assert that an actor is spawned, when it is used, or its effective gameplay behavior. Implementation needs an additional target-class guard; adding a property-name policy alone is insufficient. The current v2 serialized shape can accommodate the new kind without a schemaVersion bump, provided producer, validators, fixtures, and consumers are updated together.

The reproducible [11-domain census](artifact_item_actor_relation_semantic_design_census.json) is generated by `python3 scripts/audit-artifact-item-actor-relation-design.py --output docs/artifact_item_actor_relation_semantic_design_census.json`. It verifies manifest compressed and uncompressed hashes, exact selected candidate/source package, source shard and package hash, root edge ID and source range, local target package, target class export, superclass chain, and CDO template. Exact source and target shard JSON pointers, full target object paths, package hashes, class super edge IDs, and all target CDO relation names are in each row. The older [23-domain foundation census](artifact_formal_value_relation_foundation_census.json) independently records the same root edges and traversal states.

## Target semantic boundary

All 11 target packages are under their source item's `Actors/Items/...` family and contain the referenced Blueprint generated class export. Every class has one explicit `super` hop directly to `/Script/Dungeons.ItemActor`, stopping at `native-boundary`. Every corresponding CDO is `Default__<class>` with `class = <class>` and `template = Default__ItemActor`. Every target CDO explicitly links `Paperdoll` and `RootComponent` to a local `Paperdoll` export; these are component/presentation wiring, not evidence of a spawned projectile or effect. There is no target-side explicit gameplay relation shared by these 11 CDOs beyond the class role. The class, `super` edge ID, CDO name, template, and target-side edge names are individually recorded in the census.

This supports one common relation: the Artifact's selected source item configures an `ItemActor` subclass. It does **not** establish runtime instantiation, activation timing, cooldown, damage, or any value. The native `ItemActor` implementation remains unavailable. The meaningful exceptions are traversal bookkeeping (`followed` for powershaker and satchel-of-elixirs, `already-visited` for nine), asset spelling/case, and the fact that five source domains also configure a separate GameplayEffect. None changes target class role.

## Candidate semantics

| candidate | definition and source dependency | category dependency / target fit | future family and false-inclusion risk | RelationRef stability | decision |
| --- | --- | --- | --- | --- | --- |
| `item-actor` | Source item's configured class whose verified target directly derives from native `ItemActor`; `ItemActorClass` is the current discovery path, not the definition. | No category assumption in the semantic; exact fit to all 11 targets. | May cover another source category only after the same target-role proof. Guard prevents BeeNest, generic Actor, projectile, mine, mover, etc. | `relation:<domainId>:item-actor@1` remains stable if a future Raw property is renamed but role is unchanged. | **Choose.** |
| `artifact-actor` | Any actor associated with an Artifact. | Requires Artifact category but target role is too broad. | Would invite fishing rod, shockwave, mine, totem, and other distinct class fields. | Identity may change when a second actor role appears in one domain. | Reject. |
| `spawned-actor` | Class spawned by an activation. | Category independent, but spawning is not proved for these 11 from CDO/Structural source. | Would collide conceptually with explicit `ClassesToSpawn[0]` and actor classes with unknown runtime use. | Built on unverified runtime behavior. | Reject. |
| `actor-class` | Any class assignable to an Actor. | Target role too general; `ItemActor` specificity is lost. | Incorrectly groups all listed other actor/class fields. | One domain can own multiple actor-class roles, so the ref cannot distinguish them. | Reject. |
| defer Formalization | Keep only Raw `ItemActorClass`. | Avoids semantic assertion. | Appropriate if superclass/target role were unresolved; they are verified for all 11. | No new ref. | Reject for this exact wave, retain fail-closed gates. |

`item-actor` deliberately resembles the native target type, but its authority is the **target superclass and CDO role**, not a mechanical rewrite of the Raw field spelling. Included source edges are only the 11 exact root edges in the table. Excluded edges include traversed `ItemActorClass` if ever seen, other root actor/class fields, structural `super`/`template`, `Effect`, `GearActor`, and ranged `Projectile`.

Existing kinds do not express this boundary: `attack-sequence` is a configured melee attack sequence; `projectile` is a ranged `ProjectileDefinition` child with collection/sourceIndex identity; `gear-actor` is an Armor root `GearActor` relation and must preserve its Armor meaning; `effect` targets GameplayEffect packages. The Artifact `ItemActorClass` target is a direct `ItemActor` subclass. Sharing an `Actor`-like name with Armor GearActor or a projectile does not make their source roles interchangeable.

## Schema, occurrence, adapter and coexistence

**Schema decision: A — v2-compatible `RelationKind` extension.** `FormalSerializedRelationArtifact` already has `schemaVersion: 2`, a generic scope occurrence, `SerializedTarget`, target resolution and evidence records. `RelationRef` contains the kind and is domain parameterized; `projectionRef` contains that ref and the scope suffix. The new records add a kind while preserving existing records byte-for-byte. No serialized field, occurrence JSON shape, or existing identity changes. This is compatible for the **controlled repository consumer set** only after updating the TypeScript `RelationKind` union, generator lane, validators, integration audits, fixtures, count locks and documentation in one implementation wave. An external consumer with a closed list of four kinds would need an update; compatibility is not inferred from the union alone. Repository search found the relevant readers in `src/domain/formal/serializedRelation.ts`, `integrationAudit.ts`, `valueAvailability.ts`, Formal source/generator scripts, the serialized relation audit, and tests. Value's relation dependencies select particular existing refs and do not imply ItemActor Value population.

**Occurrence:** Each of the 11 selected root domains owns exactly one edge, so use `{ domainId, scopeRef: "source" }`. `relation:<domainId>:item-actor@1` and `projection:relation:<domainId>:item-actor@1:source` are unique against all 214 committed refs/projections and against one another. No collection or `sourceIndex` is justified. A future array or second same-role occurrence requires a separate design, not silent coalescing.

**Adapter:** Reuse the existing scope resolver's exact catalog/domain and Identity package binding, selected candidate, `rp-root`, unique root edge and exact edge ID, source shard dataset/hash, package hash, Structural edge/source relation equality, same-source matched Identity gate, local import target, and scope occurrence. Add an explicit Artifact `ItemActorClass` policy and **a target-role guard**: resolve the exact target Structural package via verified shard; require target object to be a generated class export, its direct superclass edge to be `/Script/Dungeons.ItemActor`, its inheritance chain to end at that native boundary, and the matching CDO to use `Default__ItemActor` as template. If any of these are missing/ambiguous or source/target hashes drift, fail closed. The present resolver's `requireFirstWaveTarget` only ensures local import resolution; the extra class-role check is necessary. Do not reuse the `Effect` or Armor policy branch implicitly. Target full Raw snapshot verification remains `not-supplied / not-resolved / target-snapshot-not-supplied` unless a separate input is supplied; Structural local resolution is not full Raw verification.

**Existing Effect coexistence:** `death-cap-mushroom`, `iron-hide-amulet`, `powershaker`, `shadow-shifter`, and `shock-powder` already have `effect` relations. For each, `effect` and `item-actor` have distinct RelationRefs/projectionRefs while both legitimately use the same source-scope occurrence. The model keys semantic relation/projection identity by ref plus occurrence and allows multiple relations in one domain; it has no one-domain-one-relation constraint. Each new actor edge has its own Structural pointer, package hash and evidenceRef; the existing Effect evidence and provenance must remain unchanged.
